How Cribelo works

Cribelo reads the diff of a branch and gives back three things: the lines that still need a human, the facts the diff does not show, and the order to read the files in. No model runs behind it, so the same change gets the same answer on every machine.

From the diff to the plan

The change is the diff between the merge base of your branch and your working tree. Generated files, lock files and binaries are set aside. The rest is parsed before and after the change with the tree-sitter parsers of AST Metrics, then goes through three passes.

Hunks

The first pass decides what is left to read. Every hunk of the diff gets one nature. The first rule that applies wins, and the nature sets how many lines you read.

NatureRuleYou read
movedHalf or more of its lines sit in a function that arrived from another place with the same body, identifiers aside.2 lines, plus every new line
extractedIts added lines are a function cut out of one that shrank.2 lines
renameIt differs from its old lines by one consistent old → new mapping of identifiers, seen in two hunks at least. The old name is gone from the file.1 line
formatSame tokens, whitespace aside.nothing
commentOnly comments differ.nothing
importsImport statements only.nothing
behaviorEverything else.every code line: blank, comment and import lines are not counted

A move is matched function by function: same tokens, same tokens once identifiers are normalized, or 80 % of common fingerprints, the method of RefDiff. Then it is carried line by line. A line of the moved hunk that was not in the original function, or that names something the original never named, is new, and you read it. A file whose every hunk is mechanical never enters the reading list. It is listed under Skip with its reason: moved code only, renames only, formatting only.

Read closely, or glance at

The code lines left are then split by what holds them. A line in a function that gained no decision and stays simple (cyclomatic complexity at most 3 after the change) is glanced at. So is a line outside every function, a declaration, a field, a constant, unless it branches itself. A line in a function that gained a branch, or in a function that was already complex, is read closely. The check of a rename and the look at where a block went are glances too. Reading time counts twenty lines read closely a minute, sixty glanced at.

Facts

The second pass looks for what the diff does not show. A fact is something a reader can check in a minute. Cribelo computes the import graph of the repository before and after the change and compares them, asks git for the history of each touched function, and reads your coverage report. None is a prediction. At most one fact of each kind per file.

introduces a cycle

A new import of the file leads back to the file. Barrels (index.ts, __init__.py) and Rust mod declarations do not count. One fact per cycle, three at most.

depends on a module for the first time

A directory imports a directory it never imported. A directory that did not exist before says nothing: it depends on everything for the first time.

first use of a library

A package no file of the repository imported before. The standard library and the packages the repository defines itself do not count.

went from 2 to 3 parameters, called from N files

An exported function changed its signature. The files that call it are counted, so you know how far the change reaches.

new exported functions called nowhere yet

Exported functions the change adds and no other file calls yet: either the callers come in a later change, or the function is dead on arrival.

similar to a function the change does not touch

A clone of a touched function, left as it was. Either both needed the change, or neither did.

fixed N times in the past year

git log -L on the lines of the function. One line per file, the most repaired functions first. A function fixed twice is worth a second look.

changed lines not run by any test

Read from the coverage report of your last test run: lcov, Cobertura, Clover or a Go profile. Stated from ten uncovered lines, or half of the changed ones.

Order

The third pass puts the files in reading order. The files to read are grouped. Two files are in one group when one imports the other, or, in one directory, when one calls a function the other declares. Inside a group, a file comes before the files that use it: you read the definition before its uses, the rule of Baum and colleagues (2017). Each test comes right after the file it exercises, and a test that sits next to changed code is matched in its own directory only. Groups carrying a cycle, a signature change, a fix record, a first dependency or a clone come first, then the best score, then size.

Where the score comes in

Four things shape the plan. Each one settles only what the previous ones left open, and the score comes last.

  1. NaturesWhat is read at all, and how many lines of each hunk. A file whose hunks are all mechanical never enters the list, whatever its score.
  2. FactsWhich group comes first: a cycle, a signature change, a fix record, a first dependency or a clone pulls its group to the top.
  3. DependenciesThe order inside a group: the definition before its uses, each test right after the file it exercises.
  4. ScoreWhat is left: which files fit a budget, the tie between two groups, and the high, medium and low levels shown in the table. Ten public signals, weights you can recalibrate on your own history.

Under a budget

cribelo --budget 30m fills the time with the best-ranked files first, at twenty lines read closely a minute and sixty glanced at, and adds a test only while it fits. What does not fit is listed under Skip as ranked lower, with everything it knows about it.

A gate on what is measured

Nothing here fails a build on its own. In the Action, fail-over: 1h fails the job when reading the whole change would take more than an hour, every file counted, budget or not: the change is too large for one reviewer. fail-on: cycle, signature fails it when the change introduces an import cycle or changes an exported signature that other files call; any kind of fact can be named. The job says why in one line, such as "reading time 1 h 17, over the 1 h allowed". The score never closes a gate: a level is an estimate, a gate needs a measure.

The rule Cribelo ships, no decision gained and complexity 3 or below after the change, glances at 52 % of the lines inside touched functions. The functions it glances at were repaired 1.3 % of the time, the ones it reads closely 2.8 %. A third of the functions repaired later sit in the glanced half, which is why a glance is a fast read and never a skip. The reach of a file did not help: functions in files no other file imports were repaired 2.5 % of the time, functions in files imported by twenty or more 1.4 %. A test touched in the same change made no difference either, 2.1 % against 1.9 %. With the lines outside any function, the glanced share of a change runs from a third in caddy and the GitHub CLI to nine tenths in spring-boot and bitwarden.

Clone, fix history and unused API are far above the 17 % base rate, signature above it. Cycle, dependency and library are facts about the structure; reviewers do not comment on them file by file, and they are not there to predict that.

Reading order

Share of the commented files among the first three files of the list: Cribelo 45 %, alphabetical order 33 %, largest files first 51 %. The order of Cribelo puts the definition before its uses so that the reader understands what follows; this proxy does not measure understanding.

Not measured

  • The reading time, twenty lines a minute, is a convention taken from RAID (Brito and Valente, 2021), not a measurement.
  • Hunk natures were checked by hand on samples in every language, then on twelve recent pull requests of ruff, hugo, efcore, Avalonia, jellyfin, spring-boot, keycloak, symfony, django, tokio and pydantic. Checked by one person, not measured against a labelled set.
  • Coverage facts were tested on fixtures and on one real run (AST Metrics pull request #196 with its Go profile): no repository of the bench ships a coverage report at the replayed commit.

Limits

Cribelo does not find bugs and never says a file is safe. It says what is left to read, what it knows for sure about the structure, and in which order to read. It does not know your layering rules either: a dependency from the domain to the infrastructure is a first dependency like any other. The score that settles the budget and the gate comes from ten signals (lines, complexity, coupling, fixes, churn, tests, clones); its weights are public, and cribelo calibrate learns them from your own history. Every rule, threshold and weight is in docs/how-it-is-computed.md.

The parsers, the complexity model and the dependency graph come from AST Metrics. Move matching follows RefDiff (Silva and Valente, 2017); the reading order follows Baum, Schneider and Bacchelli (2017).
